# 当前主线执行手册：Qwen3.5-0.8B 中文压缩改写器

## 1. 本文档的地位

本文档是当前项目的**唯一主线执行说明**。

后续无论是人类组员还是其他 Agent，要继续推进本项目，都应优先阅读本文档，再决定是否参考其他历史调研文档。

本文档解决的问题是：

1. 为什么项目从“数学题 `think` 监督”转向“中文长文本压缩改写器”
2. 为什么当前仍复用 `Qwen3.5-0.8B + Swift + LoRA`
3. 当前模型到底训练什么输出，哪些内容处理，哪些内容不处理
4. 数据、训练、评测、接入 Headroom 时分别要遵守什么约束

## 2. 项目已发生的方向切换

### 2.1 旧阶段做过什么

旧阶段已经跑通过一条完整链路：

- 基座模型：`Qwen/Qwen3.5-0.8B`
- 训练框架：`ms-swift`
- 微调方式：`LoRA`
- 监督位置：`<think>...</think>` 内部内容
- 任务类型：中文数学应用题显式 `think` 监督

这一阶段的价值在于：

- 证明了小参数 Qwen 模型可被显式中文风格监督
- 已经验证了 Swift 训练链路、run 目录管理、LoRA 挂载方式、基础评测脚本都能跑通
- 说明“让模型学会高信息密度中文表达”在工程上是可操作的

### 2.2 为什么不能继续沿旧任务定义推进

当前目标已经不是“让模型输出更短的数学 `think`”，而是：

**做一个可内嵌到 Headroom 的中文长文本压缩器。**

这会直接改变任务定义：

- 不再以数学题为主
- 不再以 `<think>` 监督为主
- 不再把“思维内容监督”当唯一目标
- 转为监督**可见输出本身**，让模型学会压缩改写中文长段落

因此，旧阶段可复用的是：

- 模型家族
- 训练框架
- LoRA 流程
- 脚本骨架
- run 命名和目录追溯思路

旧阶段不可直接沿用的是：

- 数据字段定义
- `think` 标签格式
- 评测口径
- 任务 prompt

## 3. 当前项目的准确任务定义

## 3.1 我们现在要做的不是摘要器

当前模型不是做泛摘要，不是做自由润色，也不是做长文总结。

它是一个：

**面向中文 Agent 场景的长文本压缩改写模型**

要求如下：

- 输入是一段中文长文本
- 输出是更短的中文文本
- 输出必须尽量保真
- 输出允许轻改写
- 输出允许轻结构化
- 输出允许轻量文言化
- 输出不能为了“显得高级”而牺牲可读性和可用性

### 3.2 输出风格要求

当前推荐风格是：

- 现代中文为主
- 轻结构化表达
- 轻文言压缩感
- 保持大模型易读

允许的风格例子：

- `因为` -> `因`
- `所以` -> `故`
- `如果` -> `若`
- `下一步需要做的是` -> `下一步`
- 长散文句改成短句或分点

不允许的风格例子：

- 纯古文腔
- 大量罕见文言词
- 改写后语序过度扭曲
- 模型不易解析的“假精炼”表达

## 3.3 处理范围

### 当前主处理对象

模型只处理 Headroom 已路由出来的**中文 plain text 长段落**，重点包括：

- 中文任务描述
- 中文需求与约束
- 中文文档说明
- 中文结果解释
- 中文进度总结
- 中文交付文本
- 中文 session 中的长自然语言块

### 当前明确不处理的对象

以下内容不作为本模型的主任务：

- 原始代码块
- 原始 JSON / YAML / XML
- 原始日志流
- 原始报错堆栈
- 原始 diff / patch
- 原始搜索结果

这些内容应继续复用 Headroom 原有的结构化压缩链路。

### 重要补充

虽然不处理上述原始结构化内容，但**中文长段落内部**可能自然夹杂少量工程锚点，例如：

- 文件名
- 路径
- 命令
- 参数
- URL
- API 名
- 数字条件

这类内容不会专门做成单独训练任务，但**不能从数据中强行清洗掉**，因为它们是真实使用场景的一部分。

## 4. 为什么当前仍选 Qwen3.5-0.8B

## 4.1 选择原则

当前模型选型不是单纯看通用能力榜单，而是看：

1. 是否已经在本项目里跑通过训练链路
2. 是否适合做中文生成式压缩改写
3. 是否能在本地或 AutoDL 上较稳定微调
4. 是否便于后续嵌入 Headroom 验证

## 4.2 选型结论

当前主线基座固定为：

- `Qwen/Qwen3.5-0.8B`

原因：

- 项目旧阶段已经在这条基座上完成过 LoRA 微调与评测闭环
- 它比 2B / 4B 更轻，更接近未来“可嵌入式压缩器”的方向
- 相比再换到完全新家族，它能最大化复用现有 Swift 训练资产
- 当前任务是生成式压缩改写，不再是旧版抽取式分类器，因此沿用 Qwen 生成模型更自然

## 4.3 为什么不是继续坚持旧的抽取式 encoder 路线

项目当前已经明确接受：

- 中文压缩允许轻改写
- 中文压缩允许轻文言化
- 中文压缩允许结构化输出

这意味着：

- 任务不再适合只做 `keep/drop` 抽取式分类
- 更适合做配对式 SFT：`原文 -> 压缩改写文`

因此，当前不再把“抽取式压缩”作为唯一主线。

## 4.4 关于 `--language-model-only`

这条是**必须执行的硬约束**。

`Qwen3.5-0.8B` 属于带视觉编码器的模型体系，但本项目只做文本压缩，不做视觉输入。

因此在训练和推理中，必须启用或等效启用：

- `--language-model-only`

目的：

- 跳过 vision encoder
- 减少显存占用
- 降低初始化负担
- 避免把多模态栈错误带入文本压缩任务

后续所有脚本、命令示例、文档说明，都应明确写出这一点。

如果某条命令没有体现这一约束，应视为待修正，而不是默认合理。

## 5. 当前训练任务应如何建模

## 5.1 新任务形式

当前训练样本应采用：

- 输入：原始中文长文本
- 输出：压缩后的中文文本

不再采用：

- `<think>...</think>` 包裹结构
- 数学题答案拼接格式
- “思维过程 + 最终答案”的双段式输出

## 5.2 训练范式

当前推荐训练范式：

- `LoRA SFT`
- 基于 Swift 的对话模板或单轮指令模板
- 直接监督 assistant 的**可见输出**

简单说：

- 用户给一段需要压缩的中文长文本
- assistant 直接返回压缩后的版本

## 5.3 不做什么

当前不做：

- RL
- DPO
- 多目标联合训练
- `<think>` 监督
- 抽取式字符标签训练

原因很简单：当前目标是**先做出可用 MVP**，而不是一次性把研究路线铺满。

## 6. 当前数据设计原则

## 6.1 数据核心结构

当前数据不再围绕：

- `modern_question`
- `classical_question`
- `modern_think`
- `classical_think`
- `structured_think`

来设计。

新的主数据应围绕“压缩改写”组织。

建议的基础样本字段如下：

- `sample_id`
  样本唯一 ID

- `source_type`
  数据来源类型，例如 `session_context`、`doc_chunk`、`task_brief`

- `source_name`
  来源名称，例如某文档名、某项目名、某数据批次名

- `split`
  `train` / `val` / `test`

- `language`
  当前固定应为 `zh`

- `original_text`
  原始中文长文本

- `compressed_text`
  教师生成的压缩改写结果

- `style_tag`
  压缩风格标签，例如 `lite_wenyan_structured`

- `contains_anchor`
  是否含少量文件名、路径、命令、URL、数字等锚点

- `quality_notes`
  可选，记录抽检备注

## 6.2 训练展开字段

训练展开后，推荐保留：

- `messages`
  直接送入训练模板

- `dataset_variant`
  当前可固定为 `rewrite_compress`

- `task_tag`
  建议固定为类似 `zh_plaintext_compress`

## 6.3 数据风格要求

教师生成的 `compressed_text` 必须满足：

1. 语义尽量不丢
2. 能明显缩短文本
3. 能适度结构化
4. 允许少量文言化
5. 读起来仍像现代中文
6. 夹杂的关键锚点尽量保留

## 6.4 不要把数据做成什么样

不要把数据做成：

- 纯摘要
- 大段主观总结
- 过度文言化
- 只删口水话但完全不重组结构
- 完全脱离真实 Agent 场景的教科书式文本

## 7. 教师标注原则

当前教师模型可以使用较强中文大模型，例如前面已经讨论过的 `DeepSeek V4 Pro`。

但教师目标已经改变：

- 不再要求它“只删不改”
- 改为要求它“保真压缩改写”

推荐教师约束如下：

1. 忠实保留原意
2. 优先删除冗余表达
3. 可将长句改写成短句或分点
4. 可使用轻量文言化压缩表达
5. 不得编造原文没有的新事实
6. 遇到文件名、路径、命令、数字、URL、API 名时应尽量保留

## 8. 训练与推理资产复用说明

## 8.1 可直接复用的现有资产

来自旧项目链路、当前仍可复用的资产包括：

- `local_repo/scripts/train_lora_local.py` 的 Swift + LoRA 基本骨架
- 现有 run 目录管理思路
- 现有模型 tag 规范
- 现有训练环境依赖
- 现有 AutoDL 远端训练经验

## 8.2 需要改造的地方

以下部分必须改：

- 默认 `dataset_tag`
- 数据文件路径命名
- `messages` 构造逻辑
- system prompt
- 校验脚本
- 评测脚本
- README 与任务说明

尤其要注意：

现有脚本里很多地方仍默认写着：

- `think`
- `s800_think`
- `Qwen/Qwen3.5-0.8B` 的旧数学任务语境

这些都不能直接继承为新任务默认值，而要显式迁移。

## 8.3 当前阶段不要求一次性重构干净

当前允许先：

- 复制旧脚本
- 做一套新任务专用脚本

等新主线跑通后，再考虑是否把旧脚本和新脚本统一进一个更抽象的框架。

原因：

- 当前最重要的是先得到可用压缩器 MVP
- 不是优先做漂亮抽象

## 9. Headroom 接入边界

## 9.1 当前叙事

当前不是重做 Headroom，而是：

- 复用 Headroom 的结构化压缩与内容路由
- 新增一条中文 plain-text 压缩改写支路

## 9.2 当前接入假设

接入时只让这个模型处理：

- 中文自然语言长段

而不是处理：

- 代码
- diff
- JSON
- 原始日志

## 9.3 这对数据的直接影响

数据集中可以自然保留少量工程锚点，但不应专门收集：

- 纯路径表
- 纯命令列表
- 纯错误堆栈
- 纯配置项

这些并不属于当前模型的主战场。

## 10. 评测方向

当前评测不再围绕“答案正确率”，而应围绕压缩器本身：

### 核心指标

1. 压缩率
2. 长度下降幅度
3. 信息保真
4. 关键锚点保留率
5. 中文自然度
6. 轻文言与轻结构化风格是否稳定
7. 本地推理速度

### 当前评测补充原则

锚点评测不可再被单一脚本分数主导。

当前应区分两层：

- `strict anchor`
  - URL
  - 路径
  - 文件名
  - 命令/参数
  - repo / model id
- `soft anchor`
  - 章节号
  - 编号
  - 字段名
  - 轻格式化 token

执行原则：

1. `strict anchor` 比 `soft anchor` 更重要
2. 脚本只负责筛查、排序、抽样，不替代人工判断
3. 低分 case 必须结合原文、参考压缩文、模型输出做人工审计
4. 若 `strict anchor` 稳定而 `soft anchor` 波动，不得直接下“模型能力明显变差”的结论

### 建议评测样本类型

- 中文需求说明
- 中文文档块
- 中文 session 总结
- 中文结果解释
- 混有少量路径、命令、数字的说明段落

## 11. 给后续 Agent 的执行顺序

后续 Agent 应按下面顺序执行，不要跳步：

1. 先阅读本文档
2. 再阅读 `docs/README.md`
3. 识别旧文档中哪些仍是历史路线，不要误当现行方案
4. 先完成新数据 schema 与数据样本构造
5. 再改训练脚本
6. 再做最小批量 teacher 标注
7. 再跑一轮最小训练
8. 再做速度与输出质量评测

## 12. 当前明确禁止的误区

后续执行中，禁止默认做以下事情：

1. 默认继续做 `<think>` 监督
2. 默认继续沿用数学题数据格式
3. 默认把旧 README 中的主结论当成新项目主结论
4. 默认把抽取式 encoder 压缩路线当成当前唯一主线
5. 默认忽略 `--language-model-only`
6. 默认把所有原始代码/日志也送进这个中文压缩模型

## 13. 当前一句话总结

当前项目主线已经更新为：

**基于 `Qwen/Qwen3.5-0.8B`、使用 Swift + LoRA，在 language-only 模式下训练一个面向 Headroom 中文 plain-text 长段落的压缩改写模型；它输出非 think 的可见压缩文本，允许轻结构化与轻文言化，目标是先做出可用 MVP。**
