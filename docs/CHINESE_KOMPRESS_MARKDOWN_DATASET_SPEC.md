# 中文 Kompress：Markdown 子数据集专项规范

## 1. 目标

本子数据集专门服务于：

**中文 Agent 自然语言上下文压缩中的 Markdown 场景**

重点覆盖：

- README
- 任务说明
- 需求文档
- 设计文档
- 实验记录
- benchmark 分析
- 周报 / 同步记录
- 交付说明 / 汇报材料

## 2. 为什么单独做 Markdown 子集

Markdown 不是普通文本格式，而是中文开发/科研/协作场景中最常见的信息组织载体之一。

它同时具备：

- 标题层次
- 长段落说明
- 列表约束
- 表格摘要
- 少量代码块与命令块混杂

所以 Markdown 场景的压缩目标，不是简单删词，而是：

**在保留结构线索和关键约束的前提下，压缩自然语言冗余。**

## 3. 原料优先级

优先采集：

1. `README.md`
2. 任务拆解 / 计划文档
3. 实验记录 / benchmark 文档
4. 团队同步文档
5. 交付说明 / 汇报文档

不建议优先采：

- 纯 API 文档镜像
- 大量自动生成的 Markdown
- 以代码块为主的教程

## 4. 样本单元定义

Markdown 子数据集不以“整个文件”为样本，而以 **逻辑块** 为样本。

建议 5 种块类型：

1. `md_paragraph_block`
   连续正文段落

2. `md_list_block`
   连续列表项，常见于要求、约束、步骤、结论

3. `md_section_block`
   标题 + 下属短段落 / 列表的组合块

4. `md_table_text_block`
   表格中自然语言单元格展开后的文本块

5. `md_summary_block`
   文档末尾总结、结论、todo、行动项

## 5. 块切分规则

## 5.1 保留的内容

优先保留并切块：

- 标题
- 正文段落
- 列表项
- 表格中的自然语言文本
- 结论 / 注意事项 / 下一步

## 5.2 剔除的内容

默认剔除：

- fenced code blocks
- 大段 shell 命令块
- 大段日志块
- 纯路径清单
- 纯配置片段
- 纯链接集合

## 5.3 特殊保留规则

即使混在自然语言中，也应保留为关键片段候选：

- 文件路径
- 命令名
- 库名
- 模型名
- 版本号
- 指标数值
- 文件名

## 5.4 推荐切块长度

建议控制在：

- `200~800` 中文字符为主

过短问题：

- 压缩空间太小

过长问题：

- 信息类型太混杂
- 标注难度上升

## 6. 数据 schema

建议 JSONL，一行一个块。

## 6.1 必填字段

- `sample_id`
- `dataset_version`
- `source_file`
- `source_section`
- `block_type`
- `sample_type`
- `text_original`
- `text_compressed_extractive`
- `char_labels`
- `quality_status`

说明：

- `block_type`：Markdown 专有块类型
- `sample_type`：仍映射回主数据集类型，如 `doc_chunk` / `task_brief` / `delivery_text`

## 6.2 选填字段

- `heading_path`
  例如 `项目背景 > 当前问题 > 下一步`

- `contains_table_text`
- `contains_code_inline`
- `contains_path_or_cmd`
- `critical_spans`
- `compression_ratio_char`
- `teacher_model`
- `notes`

## 7. 标注原则

教师模型的任务必须非常简单：

**请仅从原文中抽取必须保留的片段，保持顺序，不得改写。**

对 Markdown 场景要额外强调三点：

1. 标题层次不能随意丢  
   如果标题承担结构定位作用，应保留。

2. 列表中的约束条件不能漏  
   尤其是“必须 / 不要 / 限制 / 验收标准 / 注意事项”。

3. 数值与专有名词优先保留  
   例如：
   - 模型名
   - 指标
   - 文件路径
   - 命令
   - 时间
   - 版本号

## 8. 人工质检重点

Markdown 子集人工抽检时，重点看：

1. 压缩后是否还保留文档结构线索
2. 是否误删限制条件
3. 是否误删“下一步 / TODO / 验收标准”
4. 是否把代码块附近的重要自然语言一起误删
5. 是否把表格文字压坏

## 9. 第一版样本比例建议

第一版 Markdown 子集建议至少占总数据集的 `40%~60%`。

内部再分布可参考：

- `README / 项目说明`：25%
- `任务/需求/计划文档`：25%
- `实验记录 / benchmark 分析`：20%
- `同步文档 / 周报`：15%
- `交付说明 / 汇报材料`：15%

## 10. 最小可行版本建议

第一版先做 `300~500` 条高质量 Markdown 样本，用于：

- 打通切块流程
- 验证标注 prompt
- 检查字符级对齐是否稳定
- 观察压缩后是否仍保留结构与约束

如果这一支跑得顺，再扩到 `1k+`。

## 11. 当前最重要的判断

Markdown 子数据集不是锦上添花，而是：

**中文 Kompress 能否真正贴近真实 Agent 工作流的核心组成部分。**

如果这一支做不好，后面的中文压缩器很容易只会压“普通文本”，不会压真正有价值的中文上下文。
