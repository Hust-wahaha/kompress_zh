# Agent 文档原料池构建规范（高召回版）

## 1. 目标

这一阶段的目标不是立刻筛出“完美样本”，而是先构建一个 **足够大的候选原料池**。

所以原则应是：

**先高召回扩池，再分层过滤。**

不宜一开始就用过严的“必须同时满足多个条件”的规则卡死。

## 2. 总体策略

第一阶段使用 **“或”规则** 扩池：

只要满足下列任一条件，就可以先收进候选池。

### 2.1 仓库级 Agent 信号

满足任一即可：

- 存在 `CLAUDE.md`
- 存在 `AGENTS.md`
- 存在 `.github/copilot-instructions.md`
- README / docs 中出现 `Claude Code`
- README / docs 中出现 `Codex`
- README / docs 中出现 `OpenHands`
- README / docs 中出现 `Cursor`
- README / docs 中出现 `agent workflow`、`AI-assisted`、`generated by AI` 等表述

### 2.2 文档级高价值信号

满足任一即可：

- 文件在 `docs/` 下
- 文件名是 `README.md`
- 文件名含 `plan`、`task`、`progress`、`benchmark`、`report`、`design`、`spec`
- 文档内容包含明显的任务拆解、约束、实验记录、同步、下一步、交付说明

### 2.3 语言信号

满足任一即可：

- 文档主体为中文
- 文档是中英混合，但中文说明占比明显
- 文档为英文，但内容高度适合做中文化蒸馏

## 3. 不要一开始就追求“AI 文风识别”

“看起来像 AI 写的”可以作为弱信号，但不适合当硬门槛。

原因：

- 误判率高
- 很多人写作风格本来就像 AI
- 很多 AI 初稿会被人工重写

所以第一阶段不做“是否确定由 AI 写成”的硬判断。  
只要它 **处在 Agent 工作流里** 或 **高度适合作为 Agent 文档样本**，就可以先进池。

## 4. 候选池字段建议

每条候选文档至少记录：

- `repo_name`
- `repo_url`
- `file_path`
- `language_guess`
- `repo_agent_signal`
- `doc_value_signal`
- `markdown_quality`
- `contains_code_ratio`
- `contains_table`
- `contains_list`
- `contains_paths_or_cmds`
- `priority_tier`
- `notes`

## 5. 分层优先级

扩池后再打分分层。

### P0：优先处理

满足任一即可进入 `P0`：

- 中文 `.md`
- 位于 `docs/` 或 README
- 内容是任务/实验/同步/交付文本
- 仓库存在明显 Agent 信号

### P1：次优先

满足任一即可进入 `P1`：

- 英文但 Agent 信号强的 `.md`
- 中文普通软件工程文档
- 中英混合的高质量执行型文档

### P2：补充池

- 普通英文软件工程 Markdown
- Agent 信号不强，但结构和内容适合作为蒸馏原料

## 6. 扩池阶段的建议

第一阶段不要太纠结精确性，建议先做到：

- `100~300` 个候选文档
- 其中尽量包含：
  - 中文文档
  - 中英混合文档
  - 英文 Agent 文档
  - 普通高质量工程文档

有了这个池子，后续再做：

- 去重
- 质量筛选
- 片段抽取
- 中文化
- 压缩标注

## 7. 后续过滤再严格

真正严格的过滤，应该放到第二阶段：

- 剔除代码块占比过高的文档
- 剔除低信息密度文档
- 剔除纯链接导航文档
- 剔除纯 API 镜像
- 剔除明显自动生成垃圾文档

也就是说：

- **扩池阶段重召回**
- **入训练集阶段重精度**

## 8. 当前最推荐的做法

如果现在就开工，建议：

1. 先用“或”规则扫出一批 repo 和 `.md`
2. 先不争论是否真是 AI 写的
3. 先把中文和强 Agent 信号文档都收进池子
4. 再用字段打分分层
5. 最后从 `P0/P1` 中抽样做首版数据

## 9. 当前最重要的判断

在这个阶段，最怕的不是“收进来一些边缘样本”，而是：

**因为规则太严，前期根本扩不出一个足够大的候选池。**

所以你的判断是对的：  
这一阶段应该优先用 **“或”**，而不是 **“且”**。
