## 一、训练期的 `max_length`

[scripts/train_lora_local.py:97](scripts/train_lora_local.py#L97)：

`max_length`（默认 1024）的作用是**截断训练序列**：整条 `messages`（system + user + assistant）编码成 token 后超过 1024 的部分直接丢弃。它影响的是"训练数据能用多长"，**不会**让模型学会"在 N token 内收尾"这种行为——模型不知道自己的目标序列被截过。

本项目训练目标的典型长度（`<think>…</think>\n\n答案：N。`）在 50–200 token 之间，远低于 1024，所以 `max_length` 对实验无实质影响。

---

## 二、推理期的 `max_tokens` 是否影响"怎么输出"

这是核心问题。

### LLM 自回归生成的机制

模型每次生成第 N 个 token，依据是 token 0…N-1 的状态：

模型**不知道**自己还剩多少配额。它只是一步步往后生成，直到：
- 生成了 EOS（结束符）
- 或 `max_tokens` 被外部强制截断

当 `temperature=0`（greedy，本项目默认）时，每步的输出是完全确定的。

### 关键结论：截断等价性

**用 `max_tokens=512` 生成完整输出，再截取前 64 个 token，和直接用 `max_tokens=64` 跑推理，得到的是完全相同的 64 个 token。**

因为 greedy 下每个位置的 token 由前面的 token 唯一决定，token 0–63 的生成过程与 `max_tokens` 的设置无关。

### 那"模型会尽量在 max_tokens 前完成"是什么？

这个说法**并不正确**（至少对标准 transformer 而言）。实际现象是：

- **本项目的微调目标本身就很短**（50–200 token），所以模型在各个窗口下都"快速完成"，看起来像在配合窗口
- 模型学到的是"按这种紧凑格式输出"，不是"感知到窗口大小后压缩推理"

Qwen3.5 有个 `enable_thinking` 开关，关掉后模型不产生 `<think>` 块，输出会更短——这是代码里 [scripts/eval_five_metrics.py:147-158](scripts/eval_five_metrics.py#L147-L158) 里 baseline 关 thinking、LoRA 开 thinking 的设计原因，和 `max_tokens` 无关。

---

## 三、那 max_tokens 扫描的意义是什么？

扫描的意义不是"改变模型行为"，而是**测量"给 X 个 token 的预算，有多少比例的回答能完整收尾"**。

`extract_final_answer` 的逻辑（[src/common/style_detect.py:70-95](src/common/style_detect.py#L70-L95)）：

所以不同窗口下的指标差异，本质上就是：**完整输出被硬截断到 X token 后，还剩多少条能看到完整的 `</think>\n\n答案：N。`**。

---

## 四、能不能只跑一次 512 再后处理？

**理论上完全等价，可以这样做。** 步骤：
1. `max_tokens=512` 全量生成，保存完整 `response`
2. 对每个目标窗口 X，截取 `response` 的前 X token（注意要按 tokenizer 截，不是按字符截）
3. 对截断串分别计算指标

当前代码对每个 `max_tokens` 分别调用推理引擎，本质上是在重复跑相同的前缀生成，只是实现更简单直接。如果 GPU 时间紧，理论上可以优化成"一次生成 + 多次截断评测"，但对实验结论没有任何影响。
