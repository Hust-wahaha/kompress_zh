**类变量**。要在 assistant 回答位置预填的字符串。声明在 `class` 内、方法外，所有实例共享同一份；定义为常量是为了 `generate` 末尾拼接前缀时不重复字面量、避免两处写错。

**装饰器**。等价于把整个函数包在 `with torch.inference_mode():` 里。比 `torch.no_grad()` 更彻底：禁用 autograd、禁用 view-tracking。推理时省显存、加速，且能避免误改训练用的张量计算图。

方法签名。`prompt` 是已经填充好 `_LINKING_PROMPT.format(elements_json=...)` 之后的完整字符串。

按 **HuggingFace chat 协议**封装一条用户消息。`content` 用列表 + `{"type": ..., "text": ...}` 的格式而不是直接传字符串，是 VL 模型常见写法 —— 这样以后想塞 `{"type": "image", ...}` 不用改结构（虽然本任务用不到）。

- `apply_chat_template` 用 tokenizer 自带的 jinja 模板把 messages 渲染成模型实际看到的纯文本（含 `<|im_start|>user`、`<|im_end|>` 这类特殊符）。
- `tokenize=False` → 拿字符串，不要直接出 token id（因为我们后面还要在字符串末尾拼东西）。
- `add_generation_prompt=True` → 在末尾自动追加 `<|im_start|>assistant\n` 这种**生成起点标记**，告诉模型"轮到你回答了"。

**核心修复点**：在 assistant 起手位置直接追加 `{"relations": [`。模型现在看到的上下文不是"该你说话了"，而是"该你说话了，而且你已经开口说了 `{"relations": [`，继续往下写"。再去做 chain-of-thought 会立刻破坏 JSON 语法，贪心解码自然把它避开。

- `processor(text=[...])` 把字符串转成 token id 张量（这里没图像，所以只走 text 分支）。
- 外层 `[text]` 把单条输入包成 batch=1 的列表，是 transformers 的批接口惯例。
- `return_tensors="pt"` → 返回 PyTorch 张量（也可选 `"tf"`、`"np"`）。
- `.to(self.device)` 搬到 GPU。

- `**inputs` 把 `input_ids`、`attention_mask` 等键值一起展开传进去。
- `max_new_tokens=8192` 限制**新生成**的 token 数（不含 prompt 长度）。
- `do_sample=False` → **贪心解码**（每步取 argmax），无随机性，结果可复现。配合 prefill 才有"模型不可能续写出非 JSON 文本"的保证。

`outputs` 形状是 `[batch, prompt_len + new_len]`，开头一段就是输入 prompt 的 id。这里**沿第 1 维切片**去掉前 `prompt_len` 个 token，只保留模型新生成的部分，避免后面 decode 出整段 prompt。

- `batch_decode` 把 id 张量转回字符串列表（batch=1 所以取 `[0]`）。
- `skip_special_tokens=True` → 去掉 `<|im_end|>` 等特殊符。
- `clean_up_tokenization_spaces=False` → 不要"美化"空格（这种"美化"在中文 + JSON 场景下可能破坏格式，关掉更安全）。

**关键收尾**：模型只续写了 `{"relations": [` **之后**的部分（因为前缀在 prompt 里、被切片切掉了），所以这里把前缀拼回去，下游 `extract_json` 才能拿到一个完整闭合的 JSON 字符串。

你的方案**可行但不是最优**。先评价，再给更主流的替代。

## 你方案的有效性与短板

**有效**：模型对"特定 prefix → 特定输出分布"的关联学得很快，SFT 几千条就能让 prefix 后的 CoT 偏向文言文。

**短板有三**：

1. **风格衰减**：单个 prefix token 对开头几十 token 影响最强，越往后越弱。CoT 普遍上千 token，后半段很容易漂回模型默认的现代汉语腔。
2. **special token 本身的工程成本**：要扩展 tokenizer vocab、resize embedding、保证序列化/反序列化一致；用普通文本 cue（如 `【文言推理】`）几乎没有任何工程代价，效果在 SFT 后差不多。**用特殊 token 一般只在"该标记不应被自然语料生成"时才必要**（比如 R1 的 `<think>`），对风格控制是过度设计。
3. **风格 ≠ token**：风格是一个**分布**特征（用词、句法、语气词），不是一个起点信号；prefix 只能"启动"风格，无法"维持"风格。

## 更主流的做法（按推荐度排序）

### 1. System/user prompt 条件化 + SFT（最常用）
不用任何特殊 token。SFT 数据构造成：

模型学到的是"指令 → 风格"的整体映射。优点：
- 完全没有 infra 变动；
- 推理时可以**通过 system prompt 灵活切换风格**，比 prefill 一个固定 token 更可控；
- 数据复用性高（同样的 CoT 内容换不同风格指令就是新一条样本）。

DeepSeek-R1、Qwen3 这些推理模型的 CoT 风格本质上都是这么训出来的。

### 2. 风格 LoRA / 多 LoRA 切换
为每种风格训一个 LoRA adapter；推理时按需挂载。比方案 1 更"干净"地分离风格与基础能力，多风格场景尤其合适，**不会污染原模型的默认输出**。

### 3. RL/DPO 阶段加入风格奖励
SFT 之后再做偏好优化。reward 可以是：
- 文言文分类器打分；
- 规则项（之乎者也密度、文白词比例等）。

这能解决你最关心的"长 CoT 后半段漂走"问题——它直接对**整段**输出而不是开头打梯度。要做高质量产品级风格控制，这一步几乎是必须的。

### 4. 推理时低成本方案
不微调也能要一点效果：
- **system prompt + few-shot**：在 prompt 里给 2–3 个文言文 CoT 示例。便宜但天花板低。
- **steering vectors**：算出"文言 - 白话"的激活差向量，在 forward 时加到 hidden state 上。对简单风格（语气、礼貌度）效果尚可，对文言文这种系统性差异通常**不够稳**。

## 一句话总结

**别走 special-token-prefill 那条路**——把它换成 **system prompt 里的自然语言指令 + SFT 训练**就足够了；如果你需要 CoT 全程都不漂，再叠一层 **DPO/RL 用文言文 reward** 做整段优化。Prefill 这种技巧更适合**解构化输出**（强制 JSON、强制特定格式开头），不适合用来维持**长序列分布风格**。

可以从**三个层次**理解，从浅到深：

## 1. 工程层：本质就是"位置靠前的一段 token"

`apply_chat_template` 把你写的 system prompt 渲染成模型实际看到的字符串。以 Qwen 的模板为例：

模型完全不知道"system"这个词有什么特殊含义 —— 它看到的只是一串 token。**"system prompt 有特权"这件事，是训练数据教出来的，不是架构带来的。**

如果你把 `<|im_start|>system` 改成 `<|im_start|>user`，效果会显著变弱 —— 不是因为路径走错了，而是因为预训练/对齐时模型见过的"system 角色 → 高优先级指令"的范式不再触发。

## 2. 算法层：通过 attention 影响每一个后续 token

Transformer 是 autoregressive 的：生成第 N 个 token 时，**前面所有 token 都通过 self-attention 参与计算**。system prompt 的影响表现为：

- **KV cache 持久化**：system prompt 编码后的 key/value 张量留在缓存里，每生成一个新 token 都会被 attend 到。所以它的影响**不会随距离衰减消失**（只会被冲淡），跟 prefix token 那种"开头给个信号"完全不同。
- **位置偏置**：靠前的 token 在很多注意力头里有更强的 sink 效应（attention sink 现象），实际权重往往不低。
- **改变隐藏状态的"起点"**：从第一层开始，每一层的 hidden state 都被 system prompt 调节过；这会改变后续推理在状态空间中的"轨迹"。

直观结论：system prompt 不是简单的"开头插一句话"，而是**全程介入**每一步生成。

## 3. 训练层：为什么它"比 user prompt 更有力"

这才是最关键的一层。它的"权威性"来自三类训练数据：

**(a) 指令微调（SFT）**  
对齐阶段大量样本形如 `(system: 某规则, user: 问题, assistant: 遵守规则的回答)`。模型学到的隐式映射是："看到 system 里的规则 → 在 assistant 段产出符合规则的内容"。规则跟回答之间被反复关联，权重就被刻进了参数里。

**(b) Constitutional AI / RLHF**  
偏好数据中，**违反 system 指令**的回答被持续打低分。这让模型把"忠于 system"训成一种**收益最大化策略**。

**(c) 抗冲突训练**  
现代模型（Claude / GPT-4 / Qwen3）特意训练过"system 与 user 冲突时优先 system"的样本（典型场景：越狱攻击 / 角色注入防御）。所以你能看到很多模型即使 user 说"忽略上面的指令"，system 设定的人设依然不变。

## 串起来：一条 system prompt 的生命周期

## 实践含义（这一层才是给你用的）

1. **越靠前越强**：system prompt 比 user prompt 末尾的"再次提醒"更稳，因为它影响的是**所有后续 token**，不只是开头。
2. **长度有上限收益**：太长的 system prompt 会被自己稀释（注意力被分摊）。**简短、具体、命令式**最有效。
3. **风格类指令尤其依赖训练分布**：如果模型 SFT 阶段没见过"文言文回答"样本，你光在 system 里写也没用 —— 这就是上一轮我说**SFT 才是关键**的原因。System prompt 只是触发器，模型得"会"才行。
4. **system 不是魔法**：它的权威性是统计学意义上的，不是架构强制。Prompt injection 之所以仍可能绕过，是因为模型对"system 优先"也只是高概率倾向，不是 hard constraint。

**一句话**：system prompt 是"训练数据约定俗成的特殊位置的普通文本"——它的力量 90% 来自训练时的角色规约，10% 来自 attention 机制让它持续在场。
