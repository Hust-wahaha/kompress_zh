## 1. 关于"是否要把权重复制到项目目录"

**不建议复制权重进项目目录**,理由:

- **体积**:Qwen3.5-0.8B 已 1.7 GB,若再加 7B/9B 量级动辄 15-30 GB。git(包括 git-lfs)托管这种体量会让 clone 极慢,GitHub 也有 LFS 配额(免费 1 GB 存储 / 1 GB 带宽/月)。
- **冗余**:ModelScope/HuggingFace 已经是权威分发渠道,有官方版本号、checksum、license,复制一份反而会出现"项目内权重 vs 上游权重"的版本漂移风险。
- **license**:Qwen 系列是 Apache-2.0 / Tongyi Qianwen License,理论上允许再分发,但再分发时需要附带原始 LICENSE 与 NOTICE,合规成本不低;有些模型(如 Llama)直接禁止再分发。

**推荐的开源复现方案**:

1. 在 README 列出测试过的 model ID + commit/revision(ModelScope 与 HuggingFace 都支持指定 `revision`),让 `snapshot_download` 锁定版本。
2. 在脚本里支持 `--model` 接本地路径(当前已支持),并在 README 给出 `modelscope download --model Qwen/Qwen3.5-0.8B` 这种"先离线拉、再指本地路径"的回退指令(脚本 line 417-419 已经写了这段提示)。
3. 把**产物**(`out/` 下的 CSV、PNG、报告)入库作为 baseline,便于他人对照,而不是入库权重。
4. 可选:在 `requirements.txt` 锁版本(`transformers==x.y.z`),附 `MODELSCOPE_CACHE` 用法说明。

## 三种典型场景应该怎么做

**场景 A:两块都是大卡(单卡 ≥18 GB 显存)**
没必要动多卡。9B bf16 ≈ 17 GB 单卡放得下,顺序加载的设计就是为这种情况优化的。直接用原命令即可,GPU 0 跑完一个 LM 释放再跑下一个。

**场景 B:两块都是小卡(e.g. 单卡 12-16 GB,装不下 9B)**
需要把 9B 横跨两卡分片,目前脚本不支持。最小改动是在 [tokenizer_compression_analysis.py:467-470](tokenizer_compression_analysis.py#L467-L470) 把 `model.to(device)` 改成走 `device_map="auto"`(需要 `pip install accelerate`):

若需要,我可以加一个 `--device-map auto` 旗标走这条路,默认仍走旧 `to(device)` 路径以免引入 accelerate 强依赖。

**场景 C:想跑两块卡并行(每块装一个 LM,把顺序加载换成并发)**
当前脚本一次只跑一个 LM,改成并行需要多进程编排(每个进程绑定 `CUDA_VISIBLE_DEVICES=N`,各跑一份 control_id 列表的子集,最后 merge)。改动量大,且 0.8B+4B+9B 总时间在单卡上也只有几十分钟量级,通常不值得。

## 实用小贴士

- **指定用第二块卡**:`CUDA_VISIBLE_DEVICES=1 python tokenizer_compression_analysis.py ...`(env var 比改代码省事)。
- **同时占用 GPU 0**(被别的任务用了):`CUDA_VISIBLE_DEVICES=1` 让脚本只看见 GPU 1。
- **nvidia-smi 监控**:跑起来后 `watch -n 1 nvidia-smi` 确认显存与利用率,从而判断当前到底是单卡瓶颈还是富余。
