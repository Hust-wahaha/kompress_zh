# 中文版 Headroom 方案定位与总规划

## 1. 当前定位

我们当前项目的核心，不再是“从零做一个自己的 AI Agent 产品”，而是：

- 基于已有研究结果，验证“高信息密度压缩”在中文场景下的可行性
- 在工程落地上，**不重复造轮子**，直接复用现成的成熟框架
- 将我们的创新点收敛到一个明确模块：**中文文本压缩模型**

更具体地说，我们后续的产品化方向不是“自研一个完整的 Headroom 替代品”，而是：

- `fork` 并复用 [Headroom](https://github.com/chopratejas/headroom) 的整体架构
- 保留它现有的 proxy / wrap / MCP / CCR / memory / routing 能力
- 保留它对代码、JSON、日志、搜索结果等结构化内容的压缩能力
- 在它现有英文 `Kompress` 的基础上，新增一个**中文版 Kompress**

因此，我们的定位可以清晰表述为：

> 我们要做的不是一个新的 Headroom，而是一个可插入 Headroom 的**中文高信息密度文本压缩模型**。

---

## 2. 为什么采用这一路线

### 2.1 不重复造轮子

Headroom 已经完成了大量工程工作，包括：

- 本地代理（proxy）
- 对 Claude Code / Codex / Copilot 等 agent 的 wrap
- MCP 工具接入
- 可逆压缩（CCR）
- 多种内容类型的自动路由
- 结构化内容压缩器（代码 / JSON / logs / diff / search）

这些都不是当前课设最值得投入时间重复实现的部分。

### 2.2 我们真正的创新点在中文文本压缩

从目前调研结果看，Headroom 的 `Kompress` 系列模型主要面向英文：

- Hugging Face 模型卡明确写有 `English only`
- 语言标签为 `en`
- 基座使用 `ModernBERT`，明显偏英文自然语言场景

因此，它在中文文本压缩上的能力并不是现成可用的。

这恰好给了我们一个非常清晰的切入点：

- 复用它的工程外壳
- 替换或扩展其中的 **plain text compressor**
- 做一个真正面向中文、尤其是中文 Agent 场景的压缩模型

---

## 3. 我们到底要做什么

### 3.1 保留的部分

以下部分优先直接复用 Headroom：

- `ContentRouter`
- `SmartCrusher`（JSON 压缩）
- `CodeCompressor`（代码 / AST 压缩）
- `LogCompressor` / `SearchCompressor` / `DiffCompressor`
- proxy / wrap / MCP / CCR / memory 等整体框架

这些部分压缩的对象本身就是结构化内容，和中文能力关系不大。

### 3.2 我们新增的部分

我们新增的核心模块是：

- 中文 `Kompress`
- 或者说：**中文 plain-text compressor**

它主要负责压缩以下内容：

- 中文 prompt
- 中文长上下文说明
- 中文 conversation history
- 中文工具输出中的自然语言部分
- 中文 think / reasoning / analysis

### 3.3 最终形态

最终系统应当是：

- 英文自然语言：走原版英文 `Kompress`
- 中文自然语言：走我们自己的中文 `Kompress`
- 代码 / JSON / logs / search / diff：继续走 Headroom 原有结构化压缩器

也就是说，我们不是替换 Headroom，而是在它内部补上一条**中文文本压缩能力**。

---

## 4. 技术路线

### 4.1 路由层

在文本压缩前增加一层语言判别或语言主导性判断：

- 纯英文或英文主导文本：英文 `Kompress`
- 纯中文或中文主导文本：中文 `Kompress`
- 中英混合文本：先做简单策略，后续再迭代优化

初期不追求复杂，先保证可用。

### 4.2 模型层

我们的研究任务集中在中文文本压缩模型本身：

- 训练中文高信息密度压缩模型
- 保持关键信息不丢失
- 尽量减少 token 使用量
- 在真实 Agent 上下文中验证效果

### 4.3 数据层

后续数据集重点应围绕“中文 Agent 压缩”构建，而不是只围绕数学题：

- 中文任务描述
- 中文长 prompt
- 中文工具输出摘要
- 中文推理过程压缩
- 中文 instruction / planning / analysis 压缩

数学推理数据仍然重要，但不再是唯一数据来源。

---

## 5. 与当前课设主线的关系

这一路线不是偏离当前课设，而是对现有研究结果的自然升级。

我们目前已经做出的核心结论是：

- 通过显式监督 think 内容，可以实现更高信息密度的表达
- 在一定程度上可以减少 token，同时保持答案质量基本可接受

Headroom 路线给我们的价值，在于把这件事从“研究结论”推进到“可接入真实 Agent 的工程落地”。

因此，整体故事可以表述为：

1. 我们先在可控任务上验证中文高信息密度压缩可行
2. 再将其嵌入现有成熟压缩框架
3. 最终得到一个面向中文 Agent 场景的上下文压缩模块

---

## 6. 后续总规划

### 第一阶段：方案落地

- 完成 Headroom 路线调研
- 明确 fork 策略
- 明确哪些模块复用、哪些模块新增
- 固化本文档作为后续统一定位

### 第二阶段：中文压缩模型原型

- 设计中文文本压缩任务
- 构建训练 / 验证数据
- 训练一个最小可行版本中文 `Kompress`
- 先验证中文 plain-text 压缩效果

### 第三阶段：接入 Headroom

- 在 fork 版本中新增中文压缩模型入口
- 在 router 中加入语言判别
- 跑通 Claude Code / Codex 的 wrap 或 proxy 链路

### 第四阶段：课设展示与汇报

- 展示英文与中文压缩路径的差异
- 展示 token 节省量
- 展示质量保持情况
- 强调“复用成熟工程框架 + 聚焦中文创新点”的设计思路

---

## 7. 一句话总结

我们的目标不是重新做一个 Headroom。

我们的目标是：

> **基于 Headroom 的成熟框架，做一个真正可用的中文文本压缩模型，并将其接入真实 AI Agent 工作流。**
